| D18 | 2026-10-27 | `[tool.uv] exclude-newer = "2026-10-13T00:00:00Z"` | Supply-chain cooldown for the whole lockfile, including transitive packages. | D19 | 2026-10-27 | Provenance and taint state are keyed by the **task grant id**, not by an MCP session. The grant token is the credential header the MCP client is configured to send; the gateway reads it from the HTTP request and runs `stateless_http=True`. In eval, each AgentDojo task gets a fresh grant | MCP `2026-07-28` has no session (no handshake, no `Mcp-Session-Id`); handshake-era sessions live in one server process, which breaks stateless scaling (PRIMER "MCP protocol versions and sessions"; probe 27 Oct 2026). A grant already scopes one task. Known effect: reusing a grant across tasks merges their provenance and over-taints — fails safe; documented, not prevented | accepted |
| D20 | 2026-10-27 | Gateway and EnvBridge use the low-level `mcp.server.lowlevel.server.Server` (handlers passed to the constructor) with our own error mapping: every exception in our handlers is caught and returned as a fixed, redacted error; logs carry only redacted text | They re-expose schemas they did not write, which `MCPServer` (schemas from Python signatures) does not support. Error text: the low-level `Server` sends the raw exception message to handshake-era (`2025-11-25`) clients, also over stateless HTTP (`jsonrpc_dispatcher.py`, `ErrorData(code=0, message=str(e))`), and the SDK logs tracebacks with the original message (probe 27 Oct 2026). `MCPServer` itself already hides unexpected exception text from clients (`UnexpectedToolError`); the earlier belief that it returns `str(exc)` was wrong. Design: the gateway's `on_call_tool` catches every exception itself and returns a redacted `CallToolResult(is_error=True)`, so the SDK never handles or logs the exception; a logging redaction filter on the `mcp` logger is defense in depth | accepted |
| D21 | 2026-10-27 | Eval routes AgentDojo tool calls over MCP with a `FunctionsRuntime` subclass (`BridgedRuntime`, overriding `run_function`) passed as `TaskSuite.run_task_with_pipeline(..., runtime_class=...)`, instead of replacing `ToolsExecutor` | One override covers every pipeline (ground-truth replay and LLM) without forking AgentDojo's executor; the post-environment AgentDojo checks is the same object the bridge mutates. Cost: AgentDojo's `benchmark_suite_*` helpers do not pass `runtime_class` (`agentdojo/benchmark.py`), so our `eval/run.py` calls `run_task_with_pipeline` itself. Deviation: the LLM sees AgentDojo's tool list (`runtime.functions`), not the gateway's `tools/list`; M1-5a checks the two schemas are equal | accepted (validated in M1-5a) |
| D22 | 2026-10-27 | Ground-truth replay freezes the wall clock in agentdojo's `email_client` and `cloud_drive_client` (eval-only, context manager, refuses concurrent use); LLM runs are never frozen | Those modules stamp new emails and files with `datetime.datetime.now()`, so two direct replays of the same task differ and byte-identical equivalence cannot be checked (M1-5a diagnosis). `types.py:80` (`Email.timestamp` `default_factory`) can't be patched and is unused in replay (precondition a1 == a2 verifies) | accepted |
| D23 | 2026-10-27 | Audit in M1 is a synchronous JSONL write: a fail-closed `decision` event before forwarding and a `result` event after (deviation from D13 until M3-5) | Guarantees no unaudited calls. Consequences: an audit write failure blocks all calls (intended); each write briefly blocks the event loop (write + flush with no await between, so lines cannot interleave); latency numbers include it; M3-5 revisits with the queue | accepted |
| D24 | 2026-10-27 | Gateway startup fails if any configured upstream is unreachable or tool names collide | Simplest explicit behaviour for M1; a gateway never serves a partial tool list silently. Revisit with circuit breakers and reconnects in M3-6 | accepted |
| D25 | 2026-10-27 | Each upstream MCP client is held by its own supervisor task in the registry; a broken upstream is marked unavailable and its calls fail closed without being forwarded | Two separate causes, pinned on mcp 2.3.0 by `tests/integration/test_upstream_supervision.py`. **Expected anyio semantics, so this structure is correct use, not a workaround:** a failing child cancels the task that entered the task group (plain-anyio control test); with one holder for all clients, one dead upstream ends the healthy client too, and with one holder per client it stays local. `Task group is not initialized` was the gateway's own `StreamableHTTPSessionManager` after its run scope was cancelled, not an upstream (first-seen wording here was wrong). **Probable SDK defect, the trigger:** a POST `ConnectError` escapes the request task into the transport's task group, so one failed POST closes the whole client even when the upstream is healthy, while an HTTP 500 fails only that request (`docs/notes/sdk-issue-draft.md`, not filed). So in M1 one transient connect failure leaves that upstream unavailable until restart; M3-6 reconnects must cover this. Reworded 2026-11-02 | accepted |
| D26 | 2026-10-27 | The gateway keeps payload-logging library loggers (`mcp`, `httpx2`, `httpcore2`, `sse_starlette`) at INFO or above, set when a `Gateway` is built, whatever the root level | At DEBUG they log whole MCP messages and response chunks, including upstream error text the gateway cannot classify as secret (observed in M1-3 leak tests). Complements D20's catch-all and log filter | accepted |
| D27 | 2026-11-02 | Under `runs/`, git tracks only `metrics.json`, `config.yaml` and `report.md`, for cited runs; everything else there is ignored (existing `.gitignore` rule). A run's `config.yaml` must record `dirty: false` to be cited | Cited numbers stay traceable to a run id and commit without committing raw logs and traces, which are large and may hold sensitive content. Dirty runs are not cited: the code that produced them cannot be recovered from a commit | accepted |
| D28 | 2026-11-02 | Grant tokens are `tw_` + 256 random bits (`secrets.token_urlsafe(32)`). Only the SHA-256 hash is stored. Lookup is a dict keyed by the hash of the presented token; `hmac.compare_digest` is not used | Slow hashes make guessing low-entropy passwords expensive; a 256-bit random token cannot be guessed, so slowing the hash only adds per-request cost and a CPU-exhaustion route. Timing on the hash lookup can at most leak a stored hash prefix, which is useless without a SHA-256 preimage. `compare_digest` is not needed where no secret is compared directly, and comparing a found value with itself would prove nothing. Indexed hash lookup is the standard pattern and what M3-2 will do | accepted |
| D29 | 2026-11-02 | Authentication is pure ASGI middleware around the whole app: every HTTP path and method needs a valid token, and the 401 is sent before the body is read. Tokens are accepted only from `Authorization: Bearer`. MCP handlers do the authorization, and a handler with no grant denies | One check that no route or method can miss. The second lock means an app served without the middleware still fails closed. Not the SDK's `token_verifier`: it returns only valid or not, so the audit could not record a reason, and it brings OAuth settings we do not use. Not `BaseHTTPMiddleware`: a plain wrapper leaves SSE streaming untouched | accepted |
| D30 | 2026-11-02 | Authentication rejections are aggregated: one audit event per window (60 s), reason and known grant, with a count and latency sum and max. No per-request audit line or log line. A failed aggregate write is dropped and logged, and never blocks anything. The alternative, a separate bounded sink, was rejected | THREAT_MODEL T15. With a fail-closed audit (D23), one line per rejection lets a client with no token fill the disk and block every authorised call. Aggregation removes the path: output and memory are bounded by reasons, grants and elapsed time, whatever the request rate, because keys never contain request data. A bounded sink would still do attacker-driven I/O per request, and an attacker could evict older records from it. Cost: no per-request detail for rejections (no path, method or exact time), and a crash loses the open window's counts | accepted |
| D31 | 2026-11-02 | uvicorn's access log is off in the CLI. A token-shaped value in the query string is rejected as `auth_token_in_query`, even alongside a valid header, and also when percent-encoded | Access logs record query strings, so a token sent by mistake would be written to disk. The audit covers authorised requests. Cost: no plain HTTP request log in M1. A rejection tells the client to fix its configuration before tokens end up in other systems' URL logs, which we do not control | accepted |
| D32 | 2026-11-02 | In M1 a tool outside the grant is a fixed deny in the handler, checked before whether the tool exists, and `tools/list` returns only the grant's tools. M2-1 replaces the check with policy rules | Temporary exception to non-negotiable 4 until the policy engine exists; ARCHITECTURE's deny-or-hold needs it. Checking the grant first means a restricted grant cannot probe which tools exist. Filtering hides tools an agent cannot use, but a "hold" rule needs the agent to be able to request an out-of-grant tool, so M2-1 revisits it | accepted |
