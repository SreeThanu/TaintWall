| D16 | 2026-10-27 | Pin `mcp==2.3.0` (runtime), `agentdojo==0.1.35` and `anthropic==1.13.0` (`eval` group) | `mcp` 2.3.0 is the latest release (2026-10-02). `agentdojo` 0.1.35 is the latest release and its API is unstable. `anthropic` 1.13.0 (2026-10-09) is the newest release at least two weeks old; every 2.x release is under a week old and a major jump past what AgentDojo 0.1.35 was written against (it only requires `>=0.47.0`). Import and construction checked in M0-3; call-level compatibility is verified in M1-6 | accepted |
| D17 | 2026-10-27 | AgentDojo benchmark version pinned to `v1.2.2` in `eval/benchmark.py`; every suite load goes through `load_suites()`, which checks the installed package and version | Newest registered version and the CLI default; later versions fix faulty tasks. AgentDojo's `get_suites()` returns `{}` for an unknown version instead of raising, so the version is never left to a library default or an unchecked string. Counts differ from the paper's v1 (949 vs 629 security cases); results are not directly comparable with v1 results | accepted |
| D18 | 2026-10-27 | `[tool.uv] exclude-newer = "2026-10-13T00:00:00Z"` | Supply-chain cooldown for the whole lockfile, including transitive packages. Trade-off: **security patches released after this date are also blocked until the date is deliberately bumped**; bumping it is a recorded change that comes with a re-lock and a test run | accepted |
| D19 | 2026-10-27 | Provenance and taint state are keyed by the **task grant id**, not by an MCP session. The grant token is the credential header the MCP client is configured to send; the gateway reads it from the HTTP request and runs `stateless_http=True`. In eval, each AgentDojo task gets a fresh grant | MCP `2026-07-28` has no session (no handshake, no `Mcp-Session-Id`); handshake-era sessions live in one server process, which breaks stateless scaling (PRIMER "MCP protocol versions and sessions"; probe 27 Oct 2026). A grant already scopes one task. Known effect: reusing a grant across tasks merges their provenance and over-taints — fails safe; documented, not prevented | accepted |
| D20 | 2026-10-27 | Gateway and EnvBridge use the low-level `mcp.server.lowlevel.server.Server` (handlers passed to the constructor) with our own error mapping: every exception in our handlers is caught and returned as a fixed, redacted error; logs carry only redacted text | They re-expose schemas they did not write, which `MCPServer` (schemas from Python signatures) does not support. Error text: the low-level `Server` sends the raw exception message to handshake-era (`2025-11-25`) clients, also over stateless HTTP (`jsonrpc_dispatcher.py`, `ErrorData(code=0, message=str(e))`), and the SDK logs tracebacks with the original message (probe 27 Oct 2026). `MCPServer` itself already hides unexpected exception text from clients (`UnexpectedToolError`); the earlier belief that it returns `str(exc)` was wrong. Design: the gateway's `on_call_tool` catches every exception itself and returns a redacted `CallToolResult(is_error=True)`, so the SDK never handles or logs the exception; a logging redaction filter on the `mcp` logger is defense in depth | accepted |
| D21 | 2026-10-27 | Eval routes AgentDojo tool calls over MCP with a `FunctionsRuntime` subclass (`BridgedRuntime`, overriding `run_function`) passed as `TaskSuite.run_task_with_pipeline(..., runtime_class=...)`, instead of replacing `ToolsExecutor` | One override covers every pipeline (ground-truth replay and LLM) without forking AgentDojo's executor; the post-environment AgentDojo checks is the same object the bridge mutates. Cost: AgentDojo's `benchmark_suite_*` helpers do not pass `runtime_class` (`agentdojo/benchmark.py`), so our `eval/run.py` calls `run_task_with_pipeline` itself. Deviation: the LLM sees AgentDojo's tool list (`runtime.functions`), not the gateway's `tools/list`; M1-5a checks the two schemas are equal | accepted (validated in M1-5a) |
| D22 | 2026-10-27 | Ground-truth replay freezes the wall clock in agentdojo's `email_client` and `cloud_drive_client` (eval-only, context manager, refuses concurrent use); LLM runs are never frozen | Those modules stamp new emails and files with `datetime.datetime.now()`, so two direct replays of the same task differ and byte-identical equivalence cannot be checked (M1-5a diagnosis). `types.py:80` (`Email.timestamp` `default_factory`) can't be patched and is unused in replay (precondition a1 == a2 verifies) | accepted |
| D23 | 2026-10-27 | Audit in M1 is a synchronous JSONL write: a fail-closed `decision` event before forwarding and a `result` event after (deviation from D13 until M3-5) | Guarantees no unaudited calls. Consequences: an audit write failure blocks all calls (intended); each write briefly blocks the event loop (write + flush with no await between, so lines cannot interleave); latency numbers include it; M3-5 revisits with the queue | accepted |
| D24 | 2026-10-27 | Gateway startup fails if any configured upstream is unreachable or tool names collide | Simplest explicit behaviour for M1; a gateway never serves a partial tool list silently. Revisit with circuit breakers and reconnects in M3-6 | accepted |
| D25 | 2026-10-27 | Each upstream MCP client is held by its own supervisor task in the registry; a broken upstream is marked unavailable and its calls fail closed without being forwarded | MCP SDK v2 workaround (M1-3 "stop and reconsider" clause): when an upstream connection breaks, the SDK client's internal task group cancels the scope it was entered in. Entered in the gateway lifespan, one dead upstream cancelled the lifespan and broke every upstream (observed: healthy upstream then failed with `Task group is not initialized`). In its own task the failure stays local. No reconnect until M3-6 | accepted |
| D26 | 2026-10-27 | The gateway keeps payload-logging library loggers (`mcp`, `httpx2`, `httpcore2`, `sse_starlette`) at INFO or above, set when a `Gateway` is built, whatever the root level | At DEBUG they log whole MCP messages and response chunks, including upstream error text the gateway cannot classify as secret (observed in M1-3 leak tests). Complements D20's catch-all and log filter | accepted |
